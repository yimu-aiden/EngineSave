# 1.3.0 易用性走查与改法（D74–D77）

2026-11-25。用户："目前还是感觉不易用，也让那边能联动读我们这边游戏的数据，避免一个游戏多个版本的问题。"

做法：在沙箱（测试游戏、测试备份库、所有根令牌指到沙箱）里把 1.2.0 的窗口程序与命令行从头到尾走了一遍——第一次设置、扫描、找存档与确认 CANDIDATE、备份、看快照、恢复（含恢复到别的目录、合并的多版本、存档身份变了的新版本）、关联、清理（只试 `--dry-run`）、删除、镜像、导出导入、校验——列出 18 条不顺手的地方，按"影响大、风险低"排序。下面是每条的结论：1.3.0 改了的写改法与理由，没改的写原因。兼容的约束不变：已有参数与 `--json` 字段的含义不改，只做加法。

## 一、跨版本：同一个游戏的几个版本（D74）

这是最痛的一组。三种情况：

| | 1.2.0 | 1.3.0 |
|---|---|---|
| A 同一存档目录（Ren'Py 0.3→0.4 合成一个游戏） | 整体备份的快照恢复到其中一个版本：报 `several game-root sources (local, local-2)`，不说哪个是哪个目录；窗口没有对应的选项 | 恢复到的目录本身就是快照里的一个安装时，自动用它自己的本地存档；仍分不清时，报错逐个列出 `local: <目录> (0.3); local-2: <目录> (0.4)` |
| B 新版本换了存档目录（Ren'Py `config.save_directory` 变了） | 备份时悄悄新建第二条记录；恢复到新版本一律拒绝（`link` 过也拒绝），报错"choose that game's folder"误导；唯一的办法是照 README.txt 手工复制并自己改目录名 | 见下面 ①–④ |
| C 标题带版本号（RPG Maker 等 `Hero ver0.3`→`ver0.4`） | 同 B：两条记录；关联后恢复仍拒绝 | 同 B |

**① 读 Collections 的副本（`--collections`、窗口设置里的"Collections 地址"）。** Collections 把每个安装目录记成某部作品的一份副本，它知道 `Hero-0.3` 与 `Hero-0.4` 是同一部。扫描在 6.6 规则之后、只对没有对上记录的游戏，看同一部作品的其他副本在哪条记录里（Collections 记的 `enginesave_id`、记录的安装目录、`link_root`、这次扫描里同一部的其他目录）：只有一条就归过去（`collections.record_by = "collections"`），几条就都作为关联建议（`collections_same_work`），从不替用户在几条里挑。备份进去以后把目录 `link_root` 到这条记录，以后不带 Collections 也认得。同一次备份里同一部作品的两个新目录进同一条新记录。
- 为什么在 6.6 规则之后：存档身份仍是 EngineSave 自己的依据，Collections 只补它判断不了的情况（身份变了），不推翻已有的关联；扫描报告的 `collections.other_records` 指出一部作品已经被拆在几条记录里，交给用户。
- 为什么读不到只是警告：Collections 不在运行时扫描不能因此失败；EngineSave 仍是能单独用的工具。
- 为什么默认不开、命令行不读窗口设置：设置只在列出的地方生效。命令行用参数或环境变量 `ENGINESAVE_COLLECTIONS`。

**② `restore --retarget`（窗口：恢复对话框里"这是这个游戏的新版本、存档换了名字…"）。** 目标是这个游戏的新版本、存档换了名字时，快照的每个来源放到新版本用的同类位置（Ren'Py 全局存档放进新的存档目录，其他引擎按同一根令牌下新版本自己的存档文件夹），找不到对应位置的来源留在快照里并写明；仍有安全快照、预览与逐文件校验。恢复后把这个目录关联到记录，下次备份接着进这条记录。计划里 `retargeted` 列出每个挪了位置的来源。
- 为什么要用户点明（或已经关联过）：身份不同在 1.2.0 是"恢复进了别的游戏"的保护；只有用户说了"这是新版本"或之前已把目录关联到这条记录，才按新版本的位置放。
- 不带 `--retarget` 被拒绝时，报错写明可以加 `--retarget`；窗口的预览失败提示写明可以勾那一项。

**③ 按快照本身核对身份。** 一条记录（关联过新版本以后）里会有新旧两种存档目录的快照；恢复新版本自己的快照不再因为"记录的存档目录不同"被拒绝：目标游戏存档的位置包含快照里的所有外部来源时就是这个快照的游戏。

**④ 已关联的目录不用 `--retarget`。** `link` 过（或已经备份进这条记录）的目录，恢复时自动按它自己的存档位置放，计划的说明里写一句。走查发现 1.2.0 里"关联"之后备份能进旧记录、恢复却仍被拒绝，这条补上。

**⑤ `--skip-unchanged` 按同一安装比较。** 两个版本共用一条记录、轮流备份时，1.2.0 总拿"整条记录的最新快照"比，而那份来自另一个版本，于是每次都建新快照。1.3.0：最新快照来自另一个安装时，改与这个安装自己最新的快照比；最新快照就来自这个安装（或不写来自哪个安装）时与 1.2.0 完全相同。

**⑥ 备份计划提示"可能是某条记录的新版本"。** 将新建记录、但有关联建议的游戏，文字计划里多一行 `similar record: Hero (13d46f94, same name without the version); if this is a new version of it, first run: enginesave link …`。只改人读输出。

**⑦ `--from-install` 不再被静默忽略。** 快照只有一个本地来源、却不是 `--from-install` 指的那个安装时，1.2.0 照样恢复（恢复了别的版本的存档），1.3.0 退出码 2 并写明。

## 三、附件（D76）

用户在 Collections 里提出："不能让enginesave添加一个附件的保存库吗？我希望单独使用它也能调取一个游戏的存档和附件。"选了：每个游戏记录下一个"附件"文件夹；还没有 EngineSave 记录的游戏，先放在 Collections，有了记录再挪过来（Collections 管这一半）；两个程序都叫"附件"。

| 定下的 | 理由 |
|---|---|
| 位置 `games\<记录文件夹>\附件\`，中文文件夹名 | 与用户定的叫法一致；Windows、镜像到 NAS 都没问题。快照、对象库从不进这个文件夹，名字不会与 `snapshots`、`game.json` 冲突 |
| 普通文件，不分版本，不进快照与导出 | 攻略、补丁不需要历史；导出 zip 是"带走存档"，附件可能很大，不默认带上 |
| 校验、`--keep-auto`、删快照、清理游戏目录不碰它 | 它不属于任何快照 |
| 删除整条记录时默认留下，`--with-attachments` 才删 | 删记录多是"不要这些存档了"，附件常是另外找来、难再找的东西；单独确认 |
| 留下的附件由之后同名的新记录接手 | 同一游戏删了记录再备份，附件不丢；只剩附件的文件夹也不报"不在目录里的记录文件夹" |
| 添加时先写临时文件、完整后改名，`--move` 跨盘先复制再删 | 失败不留半个文件，原文件不丢；Collections 上传到临时文件后用 `add --move` 交过来 |
| 文件名清洗、重名加 ` (2)` | Windows 不许的字符、设备名、过长路径都在这里挡掉，调用方不必自己处理 |
| 镜像复制新文件与变了的文件，不删镜像里的 | 与镜像对快照的态度一致：镜像是另一份保底 |
| 窗口：选中记录后显示附件数，"打开附件文件夹""添加附件…" | 不加新列：附件数只在选中时读，备份库大时打开也不变慢 |

### 3.1 分工改了：文件只在 EngineSave（D77）

用户随后改了需求："你需要确保没有collections的单独保存文件夹，我们只用enginesave的……我们后续会用enginesave云端保存，collection的文件夹没法走这个途径。""而且我们本地管理和这个元数据管理的软件各管各的也方便维护"。于是存档与附件的文件——存放、复制、校验、镜像、以后的云端——全由 EngineSave 管；Collections 只记元数据、调用命令行，不再有自己的附件文件夹，也不再自己做跨版本复制（改用 `restore --retarget`）。

| 定下的 | 理由 |
|---|---|
| 记录记下它保存的 Collections 作品（`collections_work_ids`，`game.json` 与目录条目各一份），`--game collections:<id>` 找它 | Collections 不必先查 EngineSave 的记录 id；作品合并后旧 id 仍能找到 |
| 还没有存档的作品用 `--title` 建只有附件的记录（引擎 `null`、没有快照） | "先放 Collections"取消后，没装、没备份过的游戏也要有地方放附件；名字由 Collections 给，EngineSave 不猜 |
| 之后扫描、备份到这部作品时归到这条记录；游戏已有自己的记录时，备份把只有附件的那条并进来 | 一部作品始终一条记录；只有附件的记录没有存档，并掉不会丢任何存档 |
| `attachments merge`：附件与作品搬过去；被并的记录没有快照才删，有快照的留着、只去掉作品 | 搬快照（改清单、挪文件夹、让镜像跟上）风险大，留待以后；附件与作品的指向必须一次搬对 |
| 不改备份库格式、不迁移 | 新字段都是可选的，用户现在的 1.2 格式库直接用；唯一要注意的是 1.2.0 删整条记录会连附件删，有附件后请只用 1.3.0 |
| 附件全在库里（`games\<记录>\附件`） | 镜像、以后的云端同步都只看库这一处；以后要"大文件不上云"时，在 `game.json` 里给附件加按文件的选择即可，文件夹结构不用变 |

关于"避免被旧版本拖累"：这一轮没有发现 1.2 的兼容逻辑挡路的地方——新功能都是在已有格式上加可选字段，没有为旧版本留特殊分支；Collections 那边要求 EngineSave ≥ 1.3.0 以后，它自己的 1.2 兼容代码（导出后复制校验、自己的附件文件夹）可以整段删掉。
